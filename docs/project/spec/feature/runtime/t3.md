# T3 Runtime Adapter — Spec

## What it is

This specification defines how the compiled `t3` runtime adapter realizes the
runtime-neutral contract in `project/instrukt/spec/feature/runtime/adapter`.
Deterministic release and test-double verification of T3's consumed surfaces
live beside this document in
`project/instrukt/spec/feature/runtime/t3-contract`.

All live operational paths on T3 run exclusively over T3's host CLI,
authenticated HTTP project snapshot, authenticated WebSocket RPC, and caller
environment variables. Zero live operational paths open or read T3's
`statev2.sqlite`. Read-only `statev2.sqlite` access inside the T3 adapter is
confined strictly to the optional non-live cold text source
(`project/instrukt/spec/feature/runner/history`) and periodic thread-retention
sweeps (`project/instrukt/spec/feature/runner/thread-retention`).

## Canonical fields

### Declared capabilities

| Adapter capability | T3 realization |
| --- | --- |
| Universal live spine (`start`, `send`, `read_state`, `caller_identity`, `execution_root`, `list`) | Supported via `orchestration.launchThread`, `t3 thread send`, `t3 thread show --json`, `orchestration.getThreadProjection`, `t3 thread list --json`, `GET /api/projects`, `t3 project add`, and caller environment variables. |
| Idempotent start and send keys | Supported via `orchestration.launchThread` (fixed `commandId` and `threadId`), `orchestration.dispatchCommand` (fixed `commandId`), and live reconciliation via `orchestration.getThreadProjection`. |
| Input consumption and assignment observation | Supported via authenticated `orchestration.getThreadProjection` (`runs` and `messages`), distinguishing accepted/queued messages from messages that entered a run without reading `statev2.sqlite`. |
| Quota-aware model selection and readiness | Supported via `server.getConfig` (`providers: ServerProvider[]`) over short-lived `orchestration:read` auth tokens refreshed in the background. |
| Configured agent runtimes | Supported via `server.getConfig` provider-instance settings combined with inherited native harness home variables. |
| Workspace isolation (`create_worktree`, `attach_worktree`) | Supported via native `worktree` and `existing_worktree` launch placements; native shared delegation via T3 MCP. |
| Cold text source (non-live) | Supported via strictly read-only WAL-aware reads of T3's `statev2.sqlite`, isolated from live paths. |
| Thread retention / archiving (non-live) | Supported via `t3 thread list --project <checkout> --json`, read-only projection confirmation, and `orchestration.dispatchCommand` (`thread.archive`). |
| Multi-account provider isolation | Supported via T3 Provider Instances backed by isolated per-company harness homes (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`). |
| Remote peer-linking | Supported via authenticated container port binding and host `t3 environment link` for operator access, plus optional company-owner `t3 connect` dual access. |
| Notification (`notify`) | Unsupported on T3's published host CLI; use an explicit `runner.notify` command. |
| Conversation link (`link`) | Unsupported on live paths without an explicit native link command. |

### Native launch, mode resolution, and replay

- **Launch RPC and token scoping:** Authenticated `orchestration.launchThread`
  runs over T3's WebSocket transport using a short-lived `orchestration:operate`
  session token issued for the operation and revoked after use, passing fixed
  `commandId`, `threadId`, `projectId`, `generateTitle: false`, explicit model
  selection (`options` mapped as T3 `{id, value}` descriptors; omitted when no
  effort or settings are configured), resolved runtime and interaction modes,
  and the opening message. T3's native `createdBy: "user"` stamp on WebSocket
  launches is accepted.
- **Exact project resolution:** Authenticated `GET /api/projects` supplies live
  projects (excluding deleted projects). Compare canonical paths when available
  and otherwise resolved original paths, selecting only the one live project
  rooted exactly at the checkout. An ancestor or descendant project never
  stands in for the checkout. When absent at launch, `execution_root` in
  `ensure` mode runs `t3 project add <root>` — adding `--title company-<name>`
  for a company home at `~/.instrukt/companies/<name>/` and leaving T3's
  folder-name default for every other root — and re-reads the snapshot.
  Existing projects are reused as they are and never retitled. A refusal
  because a concurrent caller added the root first is confirmed by that
  re-read. Two live projects at one root are contradictory project evidence.
- **Mode resolution (fail fast):** After model preparation, `server.getConfig`
  supplies normalized settings, project overrides, managed limits, and
  selected-provider mode capabilities. Resolve the standalone CLI's
  `full-access/default` ceiling narrowed by managed maximum runtime mode, then
  apply effective global/project `defaultRuntimeMode` within that ceiling,
  recording any ceiling fallback explicitly. If the selected instance cannot
  support the inherited runtime mode, select its broadest supported mode no
  broader than that mode, or `approval-required` if none qualifies. An absent
  or empty native capability list preserves the inherited mode. Interaction
  stays `default`. Unknown or malformed mode values fail before launch. The
  caller persists the typed resolved pair and its resolution reason with
  project, command, and thread IDs in instrukt-owned durable state before
  native mutation; retries replay the captured request without recomputing
  modes. Present legacy threads without captured modes supply their actual pair
  through `orchestration.getThreadProjection`.
- **Placement and live replay:** Native placement uses `root`, `worktree`
  (captured remote base and `<slug>/work`), or `existing_worktree` (verified
  absolute path and branch, for a successor's retained worktree or an initial
  launch into an existing linked worktree). A launch reply can
  precede completed worktree preparation; later passes observe placement
  through `t3 thread show --json` or `orchestration.getThreadProjection`
  without resending the opening brief. Replaying a lost launch reply reuses the
  captured `commandId` and `threadId` over `orchestration.launchThread` (where
  T3's server-side command receipt deduplicates accepted creations and refuses
  re-creating a deleted thread) and verifies presence through live projection
  or show RPC — never by reading `statev2.sqlite`.

### Command translation and live observation mapping

Commands run on the computer hosting T3 and instrukt using the `t3` executable
on `PATH`, passing the registered checkout path as the project operand rather
than assuming `.`. There are no configurable command templates in this adapter
contract.

| Operation | T3 realization |
| --- | --- |
| Plain or todo start | Authenticated `orchestration.launchThread` with fixed `commandId`/`threadId`, captured project, model, options, modes, title, placement, and opening message. |
| Existing linked-worktree start | An initial launch targeting an existing linked worktree (such as a requested review) attaches it via `existing_worktree` with its verified absolute path and branch. |
| Queued send (idempotent) | Authenticated `orchestration.dispatchCommand` over a short-lived `orchestration:operate` token with a caller-persisted `commandId`; retries reuse the same `commandId`. Reconciliation inspects `orchestration.getThreadProjection` (`messages` and `runs`) and `dispatchCommand` replay responses without reading `statev2.sqlite`. |
| Plain send | `t3 thread send <id> -` (no `--wait`). A busy thread queues the text as its next turn (queue-only delivery realization; T3 exposes no live steering hook). |
| State (`read_state`) | Authenticated `orchestration.getThreadProjection` over a short-lived `orchestration:read` session token, decoding neutral operational state, presence, native project, active/latest run correlation (`runs[]`), pending-input count, settled metadata, and worktree/branch metadata (not `t3 thread show --json --messages 0`, which omits `runs[]` and opening-input text). |
| Input consumption & assignment evidence | Authenticated `orchestration.getThreadProjection` (`messages` and `runs`). Preparing and queued runs supply no consumption evidence; a persisted user message or assigned run alone never upgrades accepted or unknown state to consumed until the run enters execution. |
| Operational listing (`list`) | `t3 thread list --project <checkout> --json`. Activity time uses the later of `updatedAt` and `settledAt`; settled threads remain listed and un-settle when sent input. |
| Execution root (`execution_root`) | Authenticated `GET /api/projects` exact-root lookup; in `ensure` mode, `t3 project add <root>` followed by re-read. Door: `instrukt install` or `t3 project add <root>`. |

Coarse state translation from T3 status:

| Neutral state | T3 observation |
| --- | --- |
| `running` | `running`, `preparing`, `starting`, `resuming`, `queued`, or `waiting` (including a thread parked on delegated work); supplies no proof of input consumption. |
| `needs-input` | `waiting_for_input`, `waiting_for_approval`, or `pendingRequestCount > 0`, whatever the status. |
| `input-ready` | `idle`, `completed`, or `stopped` with no pending requests. Settled threads remain reachable and un-settle on send; listings retain native `settled` metadata. |
| `failed` | `failed`, `interrupted`, `cancelled`, or `rolled_back`. |
| `gone` | Explicit unknown-thread response (presence `absent`) or confirmed archived/unavailable thread (presence `archived`). |

Status spellings and optional metadata are verified against real T3 responses
(`project/instrukt/spec/feature/runtime/t3-contract`); an unrecognised status
or response shape, command failure, or unreachable server is an observation
error, never `gone` or success.

### Non-live read-only T3 storage capabilities

Only these two optional non-live capabilities inside the T3 adapter open T3's
`statev2.sqlite` read-only; neither runs on any live operational path:

- **Cold text source (`project/instrukt/spec/feature/runner/history`):** Over
  every conversation the source holds, returns each changed conversation by its
  native id with its own record (where present) and its finished messages,
  excluding reports of background commands T3 ran (messages whose
  `notification.source.kind` is `command` or `background_command`; subagent,
  delegated-task, and all other notifications are returned). Each returned
  message carries native ids, role, available timestamps, text, and the native
  record stripped of that text and of captured-context payloads: a `terminal`
  context record's `text`, a `review-comment` record's `diff`, an `element`
  record's `htmlPreview`, and the `htmlPreview` of each element in a
  `preview-annotation` record's `elements`, while every other member of those
  records (including a review comment's `text` and an annotation's `comment`)
  stays. The text read validates, fingerprints, and reads only the source
  tables it returns from; its fingerprint covers every row of those tables,
  including finished rows omitted from the returned output, so positions stay
  table-scoped and deterministic.
- **Thread retention (`project/instrukt/spec/feature/runner/thread-retention`):**
  - `finished_threads`: runs `t3 thread list --project <checkout> --json`.
    Finished is `settled` with `settledAt`. Quiet is a status of `input-ready`
    or `failed` with `snoozed` false and no `pendingBackgroundTasks`; any other
    status (including `unknown`), a missing or malformed `status` or `snoozed`,
    or a malformed `pendingBackgroundTasks` is not quiet (an omitted
    `pendingBackgroundTasks` reports none). Pinned is the projection row's
    `pinnedAt`, and latest activity is the latest of `updatedAt`, `settledAt`,
    and the projection row's `opens.openedAt` (epoch milliseconds), read
    read-only from the projection database by bound parameters. A listed thread
    without a projection row is returned pinned with unknown latest activity.
  - `archive`: re-reads the projection before mutating and proceeds only while
    the thread row is present with no `archivedAt` or `deletedAt`,
    `settledOverride` is `settled` with `settledAt`, no `pinnedAt`, no
    `snoozedUntil` later than now, and no `updatedAt` or `opens.openedAt` later
    than observed; no run of the thread has a status other than `completed`,
    `failed`, `interrupted`, `cancelled`, or `rolled_back`; no runtime request
    of the thread is `pending`; and no delegated task of the thread has a
    status other than `completed`, `failed`, `interrupted`, `cancelled`, or
    `idle`. Any other observed state returns `changed`. An unreadable
    projection or missing consumed tables/columns fails the archive with its
    cause and archives nothing. Otherwise the adapter issues a short-lived
    `orchestration:operate` token, sends authenticated
    `orchestration.dispatchCommand` with `thread.archive` and a fresh command
    ID, and revokes the token; T3's refusal of an already-archived thread
    returns `already archived`.

### Provider readiness, configured agent runtimes, and option translation

- **Readiness acquisition and token security:** Readiness refreshes read the
  local server's `server.getConfig` WebSocket RPC (`providers:
  ServerProvider[]`) using a read-scoped session token issued via `t3 auth
  session issue --scope orchestration:read --ttl <lifetime> --token-only
  --label instrukt-readiness`, held solely in memory, rotated before expiry
  with the prior token revoked, and revoked on stop (token lifetime and CLI
  launch limit are declared in the adapter's readiness module). Runtime
  mutations (`launchThread`, `dispatchCommand`) use separate short-lived
  `orchestration:operate` tokens revoked immediately after use. Server
  discovery, token framing, and RPC framing follow T3's internal protocol.
  Runtime-descriptor version, negotiated orchestration protocol, and consumed
  response-shape validation admit a snapshot; CLI and server release strings
  are diagnostics only. An unknown descriptor version or protocol/shape, a
  failed or slow token issue, or a failed read is reported with the operation
  and a safe failure category, never raw outputs or credentials. A token that
  cannot be revoked is logged; read-scoped and short-TTL operation tokens lapse
  at the end of their issued TTL, bounding hard-stop exposure.
- **Configured agent runtimes:** The same `server.getConfig` read answers
  publication (`project/instrukt/spec/feature/publication/agent-entrypoints`):
  each enabled provider instance and its open well-formed driver name (wire
  driver `claudeAgent` reports as `claude` for index compatibility while
  keeping canonical selection name and native loader family distinct, so an
  unfamiliar wire driver named `claude` acquires no Claude loader family;
  registry-agent identity is reported independently). Instance settings combine
  with inherited native variables (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`,
  `OPENCODE_CONFIG_DIR`, `FX_HOME`, `KIRO_HOME`, `PI_CODING_AGENT_DIR`),
  preserving pinned precedence for Codex/Claude variables and Codex overlay
  (`shadowHomePath`) links while treating nonsecret instance values ahead of
  inherited native values and defaulting to the machine user home. Generic
  instance `HOME`/`USERPROFILE`, OpenCode XDG, Grok variables, and private
  Antigravity profile derivation never select instruction targets; opaque,
  redacted, or relative paths are reported unknown with nothing guessed.
  Relocated Claude/fx targets carry `instruction_relocation_unverified`, and
  Antigravity's default target carries `runtime_home_differs`. An instance T3
  failed to create remains configured via its settings so publication can
  repair it; a default instance without a settings entry is configured when
  reported enabled. An unreachable server answers nothing.
- **Probe and quota-window facts:** Claude warning/unknown from a failed or
  incomplete auth probe is unready; Codex ready/unknown from a successful
  custom no-auth probe is usable. Missing, disabled, uninstalled,
  unauthenticated, unavailable, and error-state instances are reported with
  reasons. Reported model slugs and aliases are acquisition facts; T3's native
  `auto` and `default` picks are exempt from reported-model membership. At the
  pinned T3 release, a Claude window scoped to one model family is reported as
  `seven_day_<name>` (labelled `Weekly · <Name>`) and applies to configured
  models whose second `-`-separated segment after the provider prefix matches
  `<name>` lowercase (or the whole id when it has one segment); every other
  window applies to all configured models of the profile, and a scoped window
  matching none restricts nothing.
- **Option translation and validation:** Neutral effort maps to each harness's
  native T3 option id for native launch and native delegation alike (for
  example, Antigravity effort maps to `thought_level` with no other effort
  option). Before a new launch, native options are validated against the
  model's `server.getConfig` option descriptors: an unsupported option, an
  out-of-range choice value, a non-boolean for a boolean option, or any value
  neither text nor boolean refuses launch before thread creation naming the
  profile, model, and each rejected option; options are never silently dropped.
  Models without reported descriptors launch unchecked; retries replay captured
  options unchecked. Host CLI starts pass instance/model and report inability to
  express requested effort/options.

### Tier-1 BYOS account isolation (T3 Provider Instances)

On a Tier-1 shared host
(`project/instrukt/spec/feature/company/company-containers`), T3 realizes
multi-account provider isolation through T3 Provider Instances backed by
per-company isolated harness directories (such as distinct `CLAUDE_CONFIG_DIR`
or `CODEX_HOME` paths). Each company home selects its provider-instance
profiles in `company.yaml` (`profiles`, under
`project/instrukt/spec/feature/configuration/company-homes`), binding each
company's sessions to its own model subscription.

### Tier-2 isolated container remote topology

For a Tier-2 isolated company container
(`project/instrukt/spec/feature/company/company-containers`), T3 realizes
operator and optional technical company-owner dual access with explicit network
and authentication isolation (`sdlc/policy/security-awareness`):

- **Per-container authentication and egress isolation:** Each company
  container runs its own T3 server requiring per-container endpoint
  authentication on its published port; network reachability alone grants no
  access, and server/pairing credentials never enter logs or diagnostics.
  Container network policy blocks container egress from reaching host-bound
  runtime ports and sibling containers' published T3 endpoints, so a
  compromised agent or owner in one company container cannot reach another
  company's T3 server or the host's T3 server.
- **Operator access (`t3 environment link`):** Each container publishes its
  authenticated T3 port to the host's loopback interface (for same-host access)
  or to the host's Tailscale interface restricted to authorized operator peers
  (for remote operator machines on the operator's tailnet). The operator links
  the container into their host T3 via
  `t3 environment link http://<host>.<tailnet>.ts.net:<port>` (or loopback on
  the same host), avoiding per-container Tailscale daemons.
- **Optional technical company-owner dual access (`t3 connect`):** A company's
  technical administrator may link their own free T3 Connect account inside
  their company's container (`t3 connect`, approved on their own phone or
  browser) for direct thread inspection, steering, mobile push notifications,
  and Guest Links. That link reaches only that company's container and shares
  nothing with the operator's T3 Connect account or host environments.

## Use cases

### UC-SS26: Native delegation translates Antigravity effort to T3's thinking-level option

```gherkin
Given a developer configures an Antigravity profile with extra-high effort
When instrukt prepares native delegation inputs for a role using that profile on T3
Then the resolved native options map that effort to T3's Antigravity thinking-level option with that value
And those options carry no other effort option
```

### UC-SS28: A developer's todo pickup is accepted once T3 finishes preparing its worktree

```gherkin
Given the runner picks up a developer's eligible todo on T3
And T3 answers the launch while it is still preparing that todo's worktree
When T3 finishes preparing the worktree during that pickup
Then the pickup accepts the orchestrator in that conversation and its managed worktree
And no failed start is reported for it
And the orchestrator has received its opening brief once
```

## Known caveats

- T3 host-CLI `as soon as possible` delivery is queue-only; T3 provides no live
  steering hook or atomic queue withdrawal.
- T3's published CLI omits subagent threads from project listing and provides
  no `notify` command or worktree-removal command.
- T3's list JSON carries no worktree path; `t3 thread start` carries no
  effort/options flag (runner starts use `orchestration.launchThread` with
  resolved options, and native delegation passes resolved options).
- T3's `thread.archive` takes no server-side precondition; a message sent
  between the retention sweep's re-read and archive command can still land on
  an archived thread, whose queued run T3 cancels until unarchived.
- T3 does not record every UI thread opening in `opens.openedAt`; unrecorded
  openings do not reset quiet time.
