# T3 Runtime Adapter — Spec

## What it is

This specification defines how the compiled `t3` runtime adapter realizes the
runtime-neutral contract in `project/instrukt/spec/feature/runtime/adapter`.
T3 is the first shipped runtime adapter, isolated in its own adapter crate and
wired only at the CLI composition root so no other bounded context imports T3
internals. Deterministic release and test-double verification of T3's consumed
surfaces live beside this document in
`project/instrukt/spec/feature/runtime/t3-contract`.

All live operational paths on T3 run exclusively over T3's host CLI,
authenticated HTTP project snapshot, authenticated WebSocket RPC, and caller
environment variables. Zero live operational paths read T3's `statev2.sqlite`.
Read-only `statev2.sqlite` access inside the T3 adapter is confined strictly to
the optional cold text source (`project/instrukt/spec/feature/runner/history`)
and periodic thread-retention checks (`project/instrukt/spec/feature/runner/thread-retention`).

## Canonical fields

### Declared capabilities

| Adapter capability | T3 realization |
| --- | --- |
| Universal live spine (`start`, `send`, `read_state`, `caller_identity`, `execution_root`, `list`) | Supported via `orchestration.launchThread`, `t3 thread send`, `t3 thread show --json`, `t3 thread list --json`, `GET /api/projects`, `t3 project add`, and caller environment variables. |
| Idempotent start and send keys | Supported via `orchestration.launchThread` (fixed `commandId` and `threadId`) and `orchestration.dispatchCommand` (fixed `commandId` for queued message dispatch). |
| Quota-aware model selection and readiness | Supported via `server.getConfig` (`providers: ServerProvider[]`) over short-lived `orchestration:read` auth tokens refreshed in the background. |
| Configured agent runtimes | Supported via `server.getConfig` provider-instance settings combined with inherited native harness home variables. |
| Workspace isolation (`create_worktree`, `attach_worktree`) | Supported via native `worktree` and `existing_worktree` launch placements; native shared delegation via T3 MCP. |
| Cold text source | Supported via strictly read-only WAL-aware reads of T3's `statev2.sqlite` (`orchestration_v2_projection_threads` and `orchestration_v2_projection_messages` only), isolated from live paths. |
| Thread retention / purge | Supported via `t3 thread list --project <checkout> --json`, read-only projection confirmation, and `orchestration.dispatchCommand` (`thread.archive`). |
| Multi-account provider isolation | Supported via T3 Provider Instances backed by isolated per-company harness homes (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`). |
| Remote peer-linking | Supported via container port binding + host `t3 environment link` for zero-ops operator access, plus optional company-owner `t3 connect` dual access. |
| Notification (`notify`) | Unsupported on T3's published host CLI; use explicit `runner.notify`. |
| Conversation link (`link`) | Unsupported on live paths without an explicit native link command. |

### Native launch, mode resolution, and replay

- **Launch RPC:** Authenticated `orchestration.launchThread` over T3's
  WebSocket transport with fixed `commandId`, `threadId`, `projectId`,
  `generateTitle: false`, explicit model selection (`options` mapped as T3
  `{id, value}` descriptors), resolved runtime/interaction modes, and opening
  brief. Scoped short-lived auth tokens are revoked after use. T3's native
  `createdBy: "user"` stamp on WebSocket launches is accepted.
- **Exact project resolution:** Authenticated `GET /api/projects` supplies live
  projects (excluding deleted ones). Compare canonical paths when available and
  otherwise resolved original paths, selecting only the live project rooted
  exactly at the checkout. When absent at launch, `execution_root` in `ensure`
  mode runs `t3 project add <root>` (for a company home `~/.instrukt/companies/<name>/`,
  with `--title company-<name>`; otherwise T3's folder-name default) and
  re-reads the snapshot. Existing projects are never retitled. Two live
  projects at one root are contradictory evidence.
- **Mode resolution:** `server.getConfig` supplies normalized settings, project
  overrides, managed limits, and provider mode capabilities. Resolve the
  standalone CLI's `full-access/default` ceiling narrowed by managed maximum
  runtime mode and effective `defaultRuntimeMode`, falling back to the selected
  instance's broadest supported mode within that ceiling (or
  `approval-required` if none qualifies). Interaction stays `default`. Persist
  resolved modes with `commandId`/`threadId`/`projectId` in `instrukt.db`
  before native mutation; retries replay the captured request without
  recomputing modes. Legacy present threads without captured modes supply their
  actual pair via `orchestration.getThreadProjection`.
- **Placement and replay:** Native placement uses `root`, `worktree` (remote
  base and `<slug>/work`), or `existing_worktree` (retained verified absolute
  path and branch for a successor). Because a launch reply can precede
  completed worktree preparation, subsequent passes observe placement via
  `t3 thread show --json` / `orchestration.getThreadProjection` without
  resending the opening brief. Replaying a lost launch reply uses the captured
  `commandId` and `threadId` over `orchestration.launchThread` and confirms
  presence through T3's live projection/show RPC — never by reading
  `statev2.sqlite`.

### Command translation and observation mapping

Commands run on the host running T3 and instrukt using the `t3` executable on
`PATH`. Project operands always pass the registered checkout path rather than
assuming `.`.

| Operation | T3 translation |
| --- | --- |
| Plain / todo start | Authenticated `orchestration.launchThread` with fixed `commandId`/`threadId`, captured project/model/options/modes, title, placement, and opening message. |
| Queued send (idempotent) | Authenticated `orchestration.dispatchCommand` with captured `commandId` recorded in `instrukt.db` before frame write; retries reuse the same `commandId`. |
| Plain send | `t3 thread send <id> -` (no `--wait`). Busy threads queue the input as their next turn (`DeliveryRealization::Queued`; T3 has no live steering hook). |
| State (`read_state`) | `t3 thread show --json --messages 0 <id>` (or `orchestration.getThreadProjection`), decoding coarse state, presence, project, settled metadata, and worktree/branch metadata. |
| Operational listing (`list`) | `t3 thread list --project <checkout> --json`. Activity time uses the later of `updatedAt` and `settledAt`; settled threads stay listed and wake on send. |
| Execution root (`execution_root`) | `GET /api/projects` exact-root lookup; in `ensure` mode, `t3 project add <root>` followed by re-read. Door: `instrukt install` or `t3 project add <root>`. |
| Cold text read (history only) | Strictly read-only WAL-aware read of `statev2.sqlite` (`threads` and `messages` tables only), excluding background-command reports (`notification.source.kind` of `command` or `background_command`) and captured terminal/diff/preview context payloads (`project/instrukt/spec/feature/runner/history`). |
| Finished threads & archive (thread retention only) | `t3 thread list --project <checkout> --json` paired with read-only projection checks for `pinnedAt`, `opens.openedAt`, and quietness, followed by `orchestration.dispatchCommand` (`thread.archive`). |

Coarse state translation from T3 status:

| Neutral state | T3 observation |
| --- | --- |
| `running` | `running`, `preparing`, `starting`, `resuming`, `queued`, or `waiting` (including a thread parked on delegated work). |
| `needs-input` | `waiting_for_input`, `waiting_for_approval`, or `pendingRequestCount > 0`. |
| `input-ready` | `idle`, `completed`, or `stopped` with no pending requests. Settled threads remain reachable and un-settle on send. |
| `failed` | `failed`, `interrupted`, `cancelled`, or `rolled_back`. |
| `gone` | Explicit unknown-thread response (`Presence::Absent`) or confirmed archived thread (`Presence::Archived`). |

### Provider readiness, configured agent runtimes, and option translation

- **Background readiness refresh:** The runner issues one read-scoped session
  at startup (`t3 auth session issue --scope orchestration:read --ttl <lifetime> --token-only --label instrukt-readiness`),
  holds the token only in memory, rotates before expiry, revokes on stop, and
  reads `server.getConfig` (`providers: ServerProvider[]`). Runtime-descriptor
  version, negotiated orchestration protocol, and consumed response-shape
  validation admit a snapshot; release strings are diagnostics only. A failed
  refresh retains last known facts and never blocks starts.
- **Configured agent runtimes:** The same `server.getConfig` read answers
  publication (`project/instrukt/spec/feature/publication/agent-entrypoints`):
  wire driver `claudeAgent` reports as `claude` for index compatibility while
  keeping canonical selection name and native loader family distinct. Instance
  settings combine with inherited native variables (`CODEX_HOME`,
  `CLAUDE_CONFIG_DIR`, `OPENCODE_CONFIG_DIR`, `FX_HOME`, `KIRO_HOME`,
  `PI_CODING_AGENT_DIR`), preserving Codex overlay (`shadowHomePath`) linking,
  marking relocated Claude/fx targets `instruction_relocation_unverified`,
  marking Antigravity's default target `runtime_home_differs`, and treating
  relative or redacted paths as unknown.
- **Probe and quota-window facts:** Claude warning/unknown from a failed or
  incomplete auth probe is unready; Codex ready/unknown from a successful
  custom no-auth probe is usable. Native `auto` and `default` picks are exempt
  from reported-model membership. Claude model-family windows
  (`seven_day_<name>`, labelled `Weekly · <Name>`) apply to configured models
  whose second `-`-separated segment matches `<name>` lowercase; all other
  windows apply to all configured models of the profile.
- **Option translation and validation:** Neutral effort maps to each harness's
  native T3 option id (for example, Antigravity effort maps to `thought_level`
  with no duplicate effort option). Before a new launch, native options are
  validated against the model's `server.getConfig` option descriptors; invalid
  options refuse launch before thread creation rather than silently dropping
  options. Models without reported descriptors launch unchecked; retries replay
  captured options unchecked.

### Tier-1 BYOS account isolation (T3 Provider Instances)

On a Tier-1 shared host (`project/instrukt/spec/feature/company/company-containers`),
T3 realizes multi-account provider isolation through **T3 Provider Instances**
configured with per-company isolated harness directories (such as distinct
`CLAUDE_CONFIG_DIR` or `CODEX_HOME` paths). Each company home references its
own provider-instance profiles in `company.yaml` (`profiles: [...]` under
`project/instrukt/spec/feature/configuration/company-homes`), so multiple
companies run on the operator's computer using their own model subscriptions
without sharing the operator's personal subscription.

### Tier-2 isolated container remote topology

For a Tier-2 isolated company container (`project/instrukt/spec/feature/company/company-containers`),
T3 realizes operator and optional technical company-owner dual access as
follows:

- **Operator zero-ops access (no per-container Tailscale required):** Each
  company container runs its own T3 server with its port published to the
  host's loopback interface (for same-host access) or the host's Tailscale
  interface (when the operator links from another physical machine on their
  tailnet). The operator links the container into their host T3 via
  `t3 environment link http://<host>.<tailnet>.ts.net:<port>` (or the local
  loopback address when staying on the same host), gaining unified T3
  visibility without managing Tailscale daemons inside individual containers.
- **Optional technical company-owner dual access (`t3 connect`):** When a
  company's technical administrator wants direct visibility, mobile push
  notifications, Guest Links, or hands-on agent steering, they link their own
  free T3 Connect account inside the company's container (`t3 connect`,
  approved on their own phone or browser). Their access stays scoped strictly
  to that container, never sharing the operator's T3 Connect account or host
  environments.

## Use cases

### UC-RT1: Translate Antigravity effort to T3's `thought_level` option

```gherkin
Given a developer configures an Antigravity profile with xhigh effort in `agents.yaml`
When instrukt prepares native delegation inputs for a role using that profile on T3
Then the resolved native options map that effort to `thought_level` with value `xhigh`
And those options carry no other effort option
```

### UC-RT2: Accept todo pickup once T3 finishes asynchronous worktree preparation

```gherkin
Given the runner picks up a developer's eligible todo on T3
And T3 answers the launch while it is still preparing that todo's worktree
When T3 finishes preparing the worktree during that pickup
Then the pickup accepts the orchestrator in that conversation and its managed worktree
And no failed start is reported for it
And the orchestrator has received its opening brief once
```

### UC-RT3: Execute T3 live operations without reading `statev2.sqlite`

```gherkin
Given instrukt uses the compiled T3 runtime adapter
And T3's live CLI, HTTP project snapshot, and WebSocket RPC are available while `statev2.sqlite` is absent or unreadable
When instrukt starts a session, delivers a queued input, checks session state, lists sessions, and resolves caller identity
Then every live operation succeeds through T3's live API and instrukt's own state records
And no live operation opens or reads `statev2.sqlite`
```

## Known caveats

- T3 host-CLI ASAP delivery is queue-only; T3 provides no live steering hook or
  atomic queue withdrawal.
- T3's published CLI omits subagent threads from project listing and provides
  no `notify` command or worktree-removal command.
- T3's `t3 thread start` CLI carries no effort/options flag; runner starts use
  `orchestration.launchThread` with resolved options, and native delegation
  passes resolved options.
- T3's `thread.archive` takes no server-side precondition; a message sent
  between the retention sweep's check and archive command can still land on a
  thread being archived, which T3 cancels and the person unarchives to continue.
- T3 does not record every UI thread opening in `opens.openedAt`; unrecorded
  openings do not reset quiet time.
- Tier-2 company container orchestration is specified here and in
  `project/instrukt/spec/feature/company/company-containers` for alignment;
  automated container lifecycle implementation is a separate future delivery.
